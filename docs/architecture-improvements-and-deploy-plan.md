# 架构改进清单 + 真机部署监控方案

> 生成：2026-09-10 ｜ 场景：铁甲战士 / A0 / 全解锁 / 单角色
> 现状基线：V6 = 36.4% @ MCTS@20000；训练 0.5 s/局（16 worker，CPU 44.6%）；
> 已知瓶颈：① 战斗 MCTS 预算（variance）② 战斗评价函数短视（bias）
> ③ 宏观 credit assignment 过粗 ④ 训练侧战斗噪声

---

## 一、训练速度（按"增益/成本"排序）

### 1.1 战斗预算自适应（★推荐，中成本）

**根因链**：一局约 50 个战斗决策点，但难度天差地别——打小史莱姆 2000 次仿真就能稳定选对，
打精英/Boss 才需要 20000。现在**所有决策点一视同仁用 8000**，大量算力浪费在"闭着眼都能打对"的局面。

**方案**：按局面难度动态调预算。触发信号可选用：
- 敌方强度（精英/Boss 固定高预算）
- 玩家 HP 压力（HP 低于 30% 时拉满）
- 候选间分差（先用 1000 sims 粗扫，top1-top2 分差小于阈值才加深——这正是消融实验里证明有效的"近分才需要预算"的结论）

**预期**：训练侧 sims 总量降 30–50% → 0.5 s/局 → 约 0.3 s/局，且**不牺牲质量**（难局面预算反而更足）。
**风险**：自适应规则本身要调，引入一个新超参。**验证**：同 seed 对比固定 8000 的通关率不降即可。

### 1.2 训练侧预算课程（★低风险，小成本）

前期（0–3000 局）战斗预算 2000 快速积累样本，后期提到 8000 精修。
**逻辑**：前期策略还不会选牌，战斗精度高也没用（选错牌的损失 >> 打错牌的损失）。
**预期**：总时间省 ~20%。

### 1.3 C++ 战斗搜索多线程（难，不做）

sts_lightspeed 的 MCTS 是单线程的。多线程改造要动核心搜索循环（node 池/树锁），
风险高收益不直接。**结论：不碰。** 16 进程 × 单线程已经是当前硬件下合理配置
（实测 workers=28 触发 OpenBLAS 内存分配失败）。

## 二、平均楼层 / 通关率（按"证据强度 × 预期收益 / 成本"排序）

### 2.1 ★★★ 修战斗评价函数的 bias（最高优先）

**根因链**（今天已论证）：搜索器终端评价 `evaluateEndState` 只看战斗结束时的 HP 差。
铁甲的核心机制全是**长视界投资**（Demon Form 第 3–5 回合才回本、Corruption 要等牌组转一轮、
Barricade 靠跨回合格挡），短视界 rollout 里表现为"花 2–3 费换 0 收益"→ MCTS 系统性低估这些牌。
**这是 bias，加预算修不动**（文档 `docs/mcts-budget-and-reward-analysis.md` §1.4）。

**方案**：改 `third_party/sts_lightspeed` 的 `evaluateEndState`（我们已有重编译 recipe），
终端评价从"HP 差"扩成"HP 差 + 战斗状态潜力项"：
- 玩家力量层数 × 预计剩余回合数（力量是每回合复利）
- 已打出的能力牌数量（Demon Form/Barricade 在场 = 每回合自动增益）
- 中毒/荆棘层数、虚弱/易伤剩余回合
- 敌人意图（若下一回合攻击，格挡价值上升）

**成本**：中（C++ 改动 + 重编译 pyd + 回退验证）。
**预期收益**：直接抬高战斗质量上限 → 同时抬高通关率渐近线（`p_max`）和 RL 的训练信号质量。
**验证**：V6 权重 + 新评价函数 vs 旧评价函数，同 seed 500 种子 MCTS@20000 对照；
再跑决策分布对比（看 Demon Form/Inflame 的选择率是否上升）。

### 2.2 ★★★ 修 credit assignment（GAE 或按 Act 分段）

**根因链**：`G = final_floor + 50·win`，γ=1，**一局约 40 个决策共享同一个标量**，
PPO 的 ValueNet 形同虚设（advantage 退化成"这局好不好"）。
第 5 层的选牌和第 40 层的选牌拿到完全相同的信号——前者根本不知道自己错在哪。

**方案 A（最小改动）**：GAE(λ=0.95)，用 ValueNet 把单标量 G 拆成逐决策优势函数。
**方案 B（更简单）**：按 Act 分段——过 Act1/2/3 各给小额 bonus，通关再 +50。

**预期收益**：未知，中等。这是"表征到顶后"最可疑的下一块天花板。
**验证**：文档 §3.4 的奖励消融 B 组（paired A/B，MCTS@20000）。

### 2.3 ★★ 候选间交互特征（Deep Sets）

**根因链**：现在的 scorer 对每个候选**独立打分**（pointwise MLP）。但铁甲的宏观决策
大多是**比较式**的：三张卡里选一张、两条路里选一条。候选之间没有任何信息交换，
"这张卡好不好"和"它比另两张好多少"学的是两回事。

**方案**：给候选向量加一组**集合级特征**：候选集内 max-pool / mean-pool /
每个候选与池化结果的差值（"我比平均水平强多少"）。只改 Python 侧编码器，不改网络结构。

**成本**：低（+约 40 维候选特征）。
**预期收益**：小到中。**风险**：低，可与 2.1/2.2 并行做。

### 2.4 ★★ PBRS 势函数塑形（牌组一致性）

**根因链**：卡牌强度知识已经在**特征**里（42 字段 + 38 维语义 + 35 维流派交叉项），
但"抓了这张卡之后牌组变好还是变差"这种**状态转移的即时信号**完全没有——只能等终局。

**方案**（唯一理论安全的形式）：势函数 `Φ(s) = w1·牌组质量分 + w2·HP比例 + w3·(1−诅咒数/10)`，
奖励修正 `F(s,s') = γΦ(s') − Φ(s)`。其中"牌组质量分"用现有 card_data 的流派归属 ×
牌组当前流派强度算（特征里已有这些原料）。
**注意**：**绝不能**把"抓了高分卡"直接当动作奖励（会被刷、且抓取优先级随牌组变化），
这一点今天已论证（文档 §3.2）。

**成本**：低中。**预期收益**：小到中。**验证**：奖励消融 D 组。

### 2.5 ★ 评估侧战斗预算 20000 → 50000

已有拟合支持：`p(N) = 39.4 − 784/√N`，@50000 比 @20000 高约 **+1.9pp**。
**成本**：评估变慢，但评估不频繁，值得。**这是唯一一个有现成数字的改进。**

### 2.6 ★ 后期决策样本密度（mid-game 起始训练）

**根因链**：多数局死在 Act1–2 → **Act 3 的决策样本严重不足**（Boss 遗物选择、
后期商店、后期选牌只出现在少数局里）。模型对后期决策的经验远少于前期。

**方案**：训练数据里混入"从 Act 2/3 起始的局"——用 `gc.init_from_json` 从历史对局的
真机 JSON（或构造的 mid-game 状态）启动。**需要先有一个 mid-game 状态库**：
可以从 run_logger 的 JSONL 里挑"活到 Act3 的对局"重建状态（需要补一份状态快照记录）。

**成本**：中高（要建状态库 + 训练循环支持起始状态注入）。
**预期收益**：未知，中。优先级放后面。

### 2.7 重放池（off-policy 样本复用）

现在一局轨迹用完就扔。PPO-clip 本来就能容忍 off-policy 数据，可以存最近 400 局轨迹，
每次 update 从中采样。**预期**：样本效率 ×2–3。**风险**：旧数据分布漂移，需要限制新鲜度。

## 四、真机部署监控方案（按你的计划准备）

### 4.1 部署前的冒烟清单（真机上必须逐项过）

| # | 检查项 | 方法 |
|---|---|---|
| 1 | Communication Mod 连接与 STATE 节奏 | 手动开一局，确认 main.py 收到完整 JSON |
| 2 | 单个宏观决策闭环 | 让 AI 走一步选路，确认命令被真机执行 |
| 3 | **战斗命令闭环（最高风险）** | combat_brain 的 MCTS 出牌 → 命令格式 → 真机执行；
   已知 C++ `BattleAction` → Communication Mod 命令的翻译是桥接最脆弱的环节 |
| 4 | 药水/遗物屏决策 | 真机奖励屏结构与模拟器 accessor 输出对齐 |
| 5 | 断线/重连恢复 | Mod 掉线后 main.py 能安全暂停并重连 |

### 4.2 日志设计（真机侧，比模拟器日志更金贵——真机对局不可重放除非全量落盘）

**三层日志**：

| 层 | 内容 | 频率 | 用途 |
|---|---|---|---|
| L1 全量状态流 | Communication Mod 的每条 STATE JSON **原样落盘**（JSONL，一局一个文件） | 每个决策点 | **无损重放**：任何 bug 都能事后复现、也能喂给模拟器做对照 |
| L2 决策日志 | 每步：floor / 屏幕类型 / 候选列表 / 模型打分 top3 / 所选 / HP / 金币 / 药水栏 | 每个决策点 | 决策质量分析（精英率、休息策略等） |
| L3 结局 + 心跳 | 结局（楼层/是否通关/死亡原因）、每 60s 心跳（确认进程活着） | 每局/每分钟 | 监控面板与失败告警 |

RunLogger 已有 L2 的大部分字段，扩展为真机版（记录模型打分需要把 scorer 输出加进去）。

### 4.3 监控与分析

**监控（实时）**：每局结束推一条汇总（当前局数、通关数、平均楼层、最近 5 局轨迹），
失败/卡死自动上报。心跳丢失 → 立即提醒你检查真机。

**分析（事后，我负责，产出四份）**：

| 分析 | 内容 |
|---|---|
| A. 结果报告 | 真机通关率/平均楼层/每 Act 存活率，与模拟器同权重对照 |
| B. **同 seed 对照（金标准）** | 挑 N 个 seed 在真机和模拟器各跑一遍，逐决策对比——
   ① 决策是否一致（不一致 → 桥接 bug 或模拟器保真度差）
   ② 结果是否一致（不一致 → 找到分歧点，定位是 mod 状态同步问题还是搜索差异） |
| C. 决策分布 | 精英选择率、休息策略、商店消费、药水使用时机——和 V6/V9 的模拟器分布对比 |
| D. 事故复盘 | 任何异常（非法命令、卡死、状态不同步）→ 用 L1 日志重建现场，给出根因链 |

### 4.4 我对真机部署的两个提醒（预先说，免得那时候才发现）

1. **真机的"战斗"和模拟器不完全一致**：模拟器里的 MCTS 战斗在真机上要翻译成出牌命令，
   而真机战斗有**动画耗时**（一局真机可能 20–40 分钟，比模拟器的秒级慢几个数量级）。
   所以真机部署建议**宏观用 RL、战斗也让 AI 打**，但每局要有心理预期——10 局真机 ≈ 一个下午。
2. **A0 通关率 36% 的预期管理**：真机上可能更低（桥接开销、mod 状态同步延迟会引入新的噪声源），
   也完全可能更高（模拟器对某些机制的简化）。**同 seed 对照（分析 B）才能分清差异来源。**
