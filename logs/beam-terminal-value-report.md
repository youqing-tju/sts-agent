# Beam 终局估值 —— 通关率 45% → 86%（本项目战斗层最大改进）

> 2026-10-16 晚｜承接 `logs/sts1-solver-comparison-report.md` 的纠错清单 ①
> **一句话结论**：给 Beam 补上它一直缺的**终局信息**（叶节点 rollout 打到终局再打分）后，
> 前 100 留出种子的**通关率 45% → 86%**（McNemar 30/1，p<0.0001）、**楼层 +9.89**（配对 t=6.26，p<0.0001）。
> 且**最优配置同时是最便宜的**：`--beam-value-mode rollout --beam-depth 1`
> （真机单步 5.19 ms / P95 22 ms，限速 300 ms）。

## 1. 动机：纠错报告指出的"没有终局信息的评分"

上一轮把 STS1 战斗求解器生态查了一遍，发现本项目并存**两套互不相干的评估函数**：

| | MCTS 路径（`combat_brain.py`） | Beam 路径（`combat_beam.py`） |
|---|---|---|
| 搜索 | MCTS + **随机 rollout 到终局** | 分层 Beam，**无 rollout** |
| 评估 | **终局** `evaluateEndState`（C++，已针对 STS1 验证） | **静态中间状态** `evaluate()`（照抄 STS2 量级，从未验证） |

10 月转向 Beam 时，我们抛弃了**已验证的终局评估**，换成**从未验证的静态启发式**。
这与更早那轮「更宽 / 更深 / 更大预算 **全部变差**」完全自洽 ——
**一个不含终局信息的评分，越算只会越充分地放大自身误差。**

本轮就是把这个诊断落到实现上。

## 2. 实现（无需重编译 pyd）

`combat_beam.py` 新增：

| 组件 | 作用 |
|---|---|
| `terminal_score(bc, weights)` | 终局分。**从 `evaluate()` 原样抽出**（`evaluate` 行为逐位不变），口径对齐 C++ `evaluateEndState` |
| `rollout_value(bc, weights, max_steps)` | **把战斗打到终局**再打分 = `V_π(bc)`；π = 每步选 `evaluate()` 最高的**单步贪心** |
| `BeamSolver(value_mode=...)` | `"static"`（默认，**与改造前逐位一致**）/ `"rollout"`（每节点 1 次 rollout） |

⚠️ 两个关键设计点：

1. **`evaluate()` 只当「策略」用，不当「价值」用** —— 策略有偏 ≠ 价值有偏。
   静态启发式不擅长判断"这个局面好不好"，但足以在**下一步**挑出一张合理的牌。
2. **为什么能确定**：STS1 战斗是确定性的（抽牌堆顺序已知、敌人意图可见）→
   rollout 无采样噪声，`V_π` **完全确定**。已验证：同配置复跑前 20 种子，结果**逐项相同**。

透传：`env` / `ppo`（含 worker 子进程）/ `run_training` / `evaluate` / `main.py`（真机），
CLI = `--beam-value-mode {static,rollout}` + `--beam-rollout-max-steps`。

### 成本（`scripts/probes/_tmp_terminal_value_cost.py`）

| 操作 | 耗时 |
|---|---|
| `BattleContext` 拷贝 | 1.2 µs |
| `legal_actions` | 14.1 µs |
| 拷贝 + `execute` 一步 | 2.7 µs |
| **贪心 rollout 到终局**（均值 **14.3 步**） | **0.99 ms**（中位 0.90 / P95 2.01） |
| 参照：C++ `BattleSearcher`（sims=30） | 0.23 ms |

→ **"打到终局"只要 1 ms**，比改造前一次 `solve()`（1.2 ms）还划算，所以这条路一开始就可行。

## 3. 实验：四组 rollout 配置 vs 基线（100 局配对）

同一 checkpoint（`v14_defbeam_2k.pt`）、同 200 个固定留出种子的**前 100 个**、
同 `defensive` 预设、greedy 宏观策略、6 workers。**唯一变量 = 节点估值方式 / 深度 / 宽度**。

| 配置 | 楼层 | Δfloor | 配对 t | p(t) | 通关率 | Δwin | McNemar b/c | p(McN) | 逐种子 delta |
|---|---|---|---|---|---|---|---|---|---|
| baseline `static` W=2 d=6 | 34.11 | — | — | — | 45.0% | — | — | — | — |
| ⭐ **`rollout` W=2 d=1** | **46.78** | **+9.89** | **6.26** | **<1e-4** | **86.0%** | **+41.0pp** | **30/1** | **<1e-4** | +39/=60/−1 |
| `rollout` W=2 d=6 | 47.26 | +10.37 | 6.12 | <1e-4 | 85.0% | +40.0pp | 32/4 | <1e-4 | +39/=56/−5 |
| `rollout` W=2 d=12 | 46.00 | +9.11 | 5.09 | <1e-4 | 80.0% | +35.0pp | 28/5 | 1e-4 | +37/=56/−7 |
| `rollout` W=4 d=6 | 46.94 | +10.05 | 5.59 | <1e-4 | 82.0% | +37.0pp | 31/6 | <1e-4 | +40/=53/−7 |

**四组全部极显著**，效应量提升了**一个量级**（对比：此前调权重的战绩是 +2.60 层 / +9.5pp，
已是当轮"首次显著"）。逐种子看，**d=1 几乎零退化**（60 例完全不变、仅 **1 例**变差，且最差只掉 1 层）。

### 三个判读

1. **"没有终局信息"就是根因** —— 只换估值函数（机制、预算、权重全不动），通关率翻近一倍。
2. **`rollout` 一旦覆盖到终局，深度就没用了**：d=1 ≈ d=6 > d=12。
   深度越深反而略差（d=12 是 80%）——与"越算越放大误差"的规律一致，只是幅度小得多。
   **d=1 的节点数只有约 5~18 个**（= 合法动作数），而旧配置是 23~52 个。
3. **通关局牌组几乎没变**（30.7 → 31.3 张、遗物 4.6 → 4.5），Act3 血量略升（74.6 → 77.4）。
   → 改进**纯粹来自战斗层**，不是宏观策略变了。这也说明宏观策略还有独立的提升空间。

## 4. 验证（四层）

| 验证 | 方法 | 结果 |
|---|---|---|
| **确定性** | 同配置复跑前 20 种子，与已存 JSON 逐项比对 | **逐项相同** ✓ |
| **单元测试** | `tests/test_combat_beam.py` 36 → **46** 项（新增 10 项：终局分一致性 / rollout 确定性 / 不改入参 / 携带终局信息 / max_steps / value_mode 校验 / static 等价 / rollout 非空转） | 全绿 |
| **全量测试** | `pytest tests/` | **295 passed / 2 skipped**（原 285） |
| **真机延迟** | 150 帧 L1 真实战斗日志按真机路径重放 | 见下表 |

### 真机单步耗时（`--min-cmd-interval-ms` 默认 300 ms）

| 配置 | 均值 | 中位 | P95 | 最大 | 是否安全 |
|---|---|---|---|---|---|
| `static` d=6（改造前） | 1.38 ms | 0.62 | 4.65 | 6.97 | ✅ |
| ⭐ **`rollout` d=1** | **5.19 ms** | 1.69 | **22.18** | **74.76** | ✅ |
| `rollout` d=6 | 30.38 ms | 3.29 | 195.09 | **367.14** | ❌ **会超时** |

**150/150 帧构造 + 求解全部成功**。
→ ⭐ **`rollout d=1` 在通关率、算力、延迟三个维度同时最优**；
`rollout d=6` 虽通关率相当，但 P95 195 ms、**最大 367 ms 会突破真机限速**，故**真机不采用**。

## 5. 对照：MCTS 路径（一个需要复核的副作用）

顺手用同样的 100 种子跑了 C++ MCTS 路径（`--combat-solver mcts`，20000 sims）：

| checkpoint | 训练时战斗层 | @ MCTS(20000) | @ Beam+rollout |
|---|---|---|---|
| `v12_beam_500.pt` | Beam(static) | 29.3 层 / **3.0%** | 46.8 层 / 86% |
| `v14_defbeam_2k.pt` | Beam(static) | 23.3 层 / **0.0%** | 46.8 层 / 86% |

⚠️ **口径提示**：记忆里 MCTS 曾拿过 24% 通关率，但那是**另一个（MCTS 时代的）checkpoint**，
且 `ppo_v9_10000.pt` 与当前 obs 维度不兼容（824 vs 846）**无法复跑**，故**不可直接比较**。
能说明的是：**宏观策略与战斗求解器是共适应的** —— Beam 训练的模型在 MCTS 下表现极差。
这值得单列一条复核项（见 §6），但**不影响本轮结论**（本轮是同一 checkpoint、同一宏观策略下只换估值函数）。

## 6. 结论与下一步

### 已确定

1. ⭐ **根因确认**：Beam 缺终局信息 = 「更宽/更深/更大预算全部变差」的解释。补上后 **45% → 86%**。
2. ⭐ **新最优战斗配置**（本项目当前的战斗层基线）：
   `--combat-solver beam --beam-value-mode rollout --beam-depth 1 --beam-max-nodes 300 --beam-weights-preset defensive`
   （`beam_width` 在 d=1 下**不起作用** —— 只有一层，全部子节点都被 rollout 打分）
3. **旧的"宽度/深度调参"结论对 rollout 模式不再适用**（那套结论属于 static 估值时代）。
4. **Power 绑定盲区不再是要害**：价值来自终局模拟，静态启发式只用于选牌；
   这解释了为什么"补 Power 绑定"一直没成为瓶颈。

### 下一步（按优先级）

| 优先级 | 事项 |
|---|---|
| **P0** | **用 rollout 战斗层重训 RL** —— 战斗执行从 45% 级跳到 86% 级，宏观策略的学习环境**彻底变了**。这是项目方法论（"战斗强弱 ↔ 抓牌质量"）成立的前提 |
| **P0** | **真机配置切到 rollout d=1** 并实跑（已改 Mod 配置；见 `docs/realtime-launch-guide.md`） |
| **P1** | **强化 rollout 策略 π**：权重现在**只决定 π**（价值来自终局），所以"调权重"的目标从"评分准"变成"策略强"。可试 2 步贪心 / 复用 `defensive` 之外的方向 |
| **P1** | **复核 MCTS 路径**（§5 的 3%/0%）—— 先找一个 obs 维度兼容的 MCTS 时代 checkpoint，确认是否共适应所致 |
| **P2** | 补 Power 绑定（重编译 pyd）—— 仍能提升 π 的选牌质量，但**不再是瓶颈** |
